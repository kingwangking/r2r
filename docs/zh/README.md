# R2R — 从持续执行到成熟交付

**Plan big. Run long. Harden deep. Steer anytime.**

R2R（Run to Ready）是一种面向 AI Agent 开发大型复杂软件的工程方法。它要处理的根本矛盾是：

- **速度必须提高：** 如果每次 AI 开发都等待一轮昂贵的全面 Review，AI 的生产优势会被抵消。
- **复杂度必须能够承载：** AI 使独立开发者能够构建原本需要团队完成的大型项目，局部审查不等于整体工程可靠。
- **最终稳定性不可放弃：** 产品必须通过真实完整业务链的验收，但没有理由要求每个中间形态都达到发布质量。

**关键观点：不是不要质量，而是改变质量保证在整个开发生命周期中的分布。**

## 一个方法、三个主要动作、一项控制原则

**PLAN — 先确保方向。** 研究产品目标和用户任务、全局架构、模块职责、数据权威、现成系统复用、关键风险，建立足够完整、可以长程推进的路线图。并非事先冻结所有实现细节；方向和架构假设必须允许证据驱动的修正。

**RUN — 持续高速建设。** 让 Agent 在明确授权的范围内长周期执行，持续产生真正的产品功能。只做与当前风险相称的测试和 Review；轻量 Review 可异步、可批量，可推迟不影响后续工作的深入检查。产品中间形态允许不完善，甚至暂时不能通过某些冒烟测试。

**HARDEN — 反复收敛到成熟产品。** 当主要功能和用户路径形成后，进行真实集成、结构性重组、体验优化、系统级测试、严重缺陷修复和最终验收。前几轮常常是在重构和重新组织产品，不是简单地找 Bug。

**STEER ANYTIME — 开发者随时掌控。** 长执行是核心能力，但执行多长、何时提问、何时深入 Review、何时重构，以及中间版本需要多稳定，由开发者的系统认知、风险和实际证据灵活决定。不是固定每 N 轮必须 Review。

## 立即开始：复制到 AI 编码助手

```text
采用 R2R 方法开发当前项目。
PLAN：先理解真实仓库，形成完整产品目标、架构边界、功能路线和最终验收标准。
RUN：在我授权的范围内按规划持续实现。优先保证实质功能进展；普通变更采用轻量
验证和必要的独立 Review，不因中间形态不完美反复等待。记录实际成果、问题和恢复点。
STEER：我可以随时询问重要的业务或架构问题、要求证据、调整执行长度或 Review 深度。
HARDEN：核心能力形成后多轮整合、结构优化、真实使用测试和修复，直到产品满足验收。
真实数据、安全、权限、版权、凭据及不可逆操作的保护不可推迟。
不要把没执行的测试说成通过，也不要虚构 Agent 在会话结束后仍持续运行。
```

## 三个经常被误解的点

1. **R2R 不是跳过测试：** 它允许开发者按风险决定验证时机，但最终真实产品的验收不能省略。
2. **R2R 不是固定的超长循环：** 允许覆盖数百项任务的完整规划，持续长时间执行，也允许一个关键问题就暂停重定向。
3. **R2R 不是只能本地运行：** 使用 ChatGPT 网页端和 GitHub 就可以实践；仓库保持规划、执行事实与下一步。关闭会话后不会假装继续在后台执行。
